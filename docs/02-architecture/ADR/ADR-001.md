# ADR-001: Adopción de Arquitectura Hexagonal y Pipeline Modular Desacoplado

**Fecha**: 2026-08-18 | **Estado**: Aceptado  
**Fase PDCO**: PLAN → DEVELOPMENT  
**Estándar**: SWEBOK Cap. 2 (Software Design), ISO/IEC 25010 (Mantenibilidad & Modularidad), Clean Code  

---

## 1. Contexto

En las fases iniciales de exploración de datos en proyectos de analítica y ciencia de datos territoriales, es común la proliferación de scripts monolíticos y cuadernos interactivos (Jupyter Notebooks) acoplados con lógica de negocio, manipulación de archivos y visualizaciones dispersas.

Esta aproximación genera graves riesgos de ingeniería:
1. **Falta de Testabilidad**: Imposibilidad de ejecutar pruebas unitarias y de regresión automatizadas sobre funciones críticas.
2. **Duplicación de Código (Violación DRY)**: Repetición de rutinas de homologación territorial, normalización y cálculo de tasas per cápita.
3. **Fragilidad ante Cambios**: Modificar una fuente de datos requería editar múltiples cuadernos independientes de forma manual.

---

## 2. Decisión

Implementar una **Arquitectura Modular Hexagonal (Ports & Adapters)** que desacople estrictamente el núcleo analítico de las interfaces de consumo:

1. **Paquete Central Reutilizable (`src/`)**:
   - `src/ingestion/`: Adaptadores polimórficos de carga de datos crudos (CSV, XLSX, GPKG, GeoJSON).
   - `src/validation/`: Motores de validación de calidad y esquemas territoriales (ISO 25010).
   - `src/cleaning/`: Homologación canónica de identificadores DIVIPOLA (1 a 20 localidades).
   - `src/integration/`: Ensamblaje del Tablón Maestro Territorial consolidado.
   - `src/features/`: Feature Engineering de densidades espaciales y ratios per cápita.
   - `src/modeling/`: Motor matemático de cálculo del Índice de Priorización Territorial (IPT).
   - `src/visualization/`: Generación de matrices GeoJSON y compilador Web GIS.

2. **Consumo Desacoplado**:
   - Los **Notebooks (`notebooks/`)** operan exclusivamente como capas de presentación y análisis exploratorio, importando las funciones del paquete `src`.
   - La **Suite de Pruebas (`tests/`)** valida los contratos e interfaces del paquete `src` de forma automatizada mediante `pytest`.

---

## 3. Consecuencias

### Positivas
- **Alta Cobertura y Testabilidad**: Cobertura de pruebas $\ge 95\%$ y ejecución automatizada en CI/CD.
- **Mantenibilidad Extrema**: Modificar un algoritmo de cálculo o normalización en `src/modeling` impacta de forma unificada a todos los reportes y cuadernos.
- **Separación de Responsabilidades (SRP)**: Cada módulo posee una única razón para cambiar.

### Trade-offs / Mitigaciones
- Requiere una estructura de empaquetado estándar (`pyproject.toml`) y disciplina de desarrollo para evitar escribir lógica ad-hoc dentro de las celdas de los cuadernos.
